$ARGUMENTS 를 Repopolis 기준으로 검토한다. **문제를 찾으러 들어간다.** 맞장구로 시작하지 않고, 근거는 `viewer.html` · `scan.js` · `app/` · README · 실험실 측정에서 확인한 것만 쓴다. 확인 못 한 것은 "모름"으로 두고 무엇으로 확인할지 적는다.

## 입력

- 모드 (비우면 대상을 보고 고른다): `design` = 새 기능 · 설계안 (1~6단계), `docs` = README · 화면 안 설명과 실제 동작 대조 (7단계).
- 사용자가 이미 정한 것(예: 문서 파일 .md 는 건물에서 뺀다, 아래 재생바 대신 위 버튼)은 다시 열지 않는다. 새 근거가 있을 때만 "다시 볼 근거"로.

## design 모드

1. **대상과 걸린 결정.** 무엇을 검토하는지, 이 검토로 무엇을 정하려는지 한 줄씩. 설계안의 주장을 확인(코드 · 측정) / 가정 / 모름으로 나눈다.
2. **정체성 대조.** Repopolis 는 "내 코드가 사는 도시"다. 새 것이 저장소의 무언가를 알려 주는가(높이 = 줄 수, 차 = 커밋, 사람 = 파일, 크레인 = 커밋 안 된 변경 같은 짝이 있는가), 이미 다른 것이 알려 주는 걸 겹쳐 알리지 않는가.
3. **사용자가 겪는 것.** 30초(켜서 보기) · 3~5분(걸어 다니며 건물 찾기 · 코드 보기) · 하루(개발하며 켜 두기 — 실시간 갱신 · 트레이) 단위로, 이 기능이 각 단위에서 무엇을 보게 · 하게 만드는지. 결과가 0.5초 안에 보이는지.
4. **빈틈.** 최소 · 최대를 넣어 본다: 파일 1개 · 수천 개, 커밋 0 개(빈 저장소) · git 아님, 공사 중 0곳 · 수백 곳, 아주 긴 파일, 이름이 긴 파일, 밤, 건물 안, 작은 창. 빈 경우가 정해져 있는지, 큰 저장소에서 개수 상한이 있는지.
5. **겹치는 장면 따라가기.** 여러 일이 한꺼번에 도는 순간 3~5개: 걷는 중 실시간 갱신이 옴, 건물 안에 있는데 그 파일이 커밋됨, 타임랩스 재생 중 공사 시작, 차에 치여 구르는 중 건물 앞 E. 무엇이 먼저 도는지(파일:줄)와 실패 모양(상태 꼬임 · 화면 튐 · 두 번 실행).
6. **수용 기준 고쳐 쓰기.** "눈에 띈다", "자연스럽다"를 잴 수 있는 문장으로 (예: "공사 중 파일은 둘러보기 기본 시점에서 3초 안에 찾는다", "공사 중 300곳에서 걷기 멈칫 100ms 넘는 프레임 0"). 무엇으로 잴지(`/playtest` · `/feel` · 사진)를 붙인다.

## docs 모드

7. **README · 화면 설명 대조.** README 의 "도시 읽는 법" · 단축키 · 화면 안 도움말(`#howto` · 걷기 안내)의 내용을 코드와 맞춰 본다. 결과 분류: 충돌(설명과 동작이 다름) · 낡음 · 빠짐(코드에만 있음) · 확인 못 함. 코드에만 있는 규칙은 "의도 확인 필요"를 붙인다.

## 보고

결론 한 줄(판정 + 가장 큰 문제). 판정: `통과` · `고칠 것 있음` · `크게 고칠 것` · `판단 안 함`.

```
- [심각 | 보통 | 작음] 관찰 — 사용자에게 어떻게 닿나 — 근거(확인: 파일:줄 · 측정 / 가정 / 모름)
  가장 작은 수정: … / 확인 방법: …
```

그다음 고쳐 쓴 수용 기준 표, docs 모드면 대조 표(설명 위치 | 설명 | 실제 | 분류).

## 하지 않는 것

- 파일 수정 (읽기 · `git log` · `git diff` 만)
- 잰 적 없는 결과를 지어 쓰기 ("답답해할 것이다"는 확인 실험으로 돌린다)
- 약점을 새 기능으로 덮자는 제안. 가장 작은 수정부터
