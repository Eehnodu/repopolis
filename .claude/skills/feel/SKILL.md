$ARGUMENTS 의 손맛을 재고 따진다. **느낌을 말한 문장은 잴 수 있는 변수로 바꾼 뒤에 다룬다.** "둥둥 뜬다"를 그대로 고치지 않고, 꼭대기까지 시간 · 중력 같은 숫자로 바꿔 지금 값을 재고, 사용자가 원하는 범위를 정하게 한다.

## 입력

- 대상 동작, 또는 사용자가 한 느낌 말.
- 숫자 출처: `viewer.html` 의 `updateWalk` (속도 · 가속 · 돌기 · 점프 · 착지), `walkCamDesired` (카메라 거리 · 높이 · 가림), `hitByCars` (차에 치임), `sitDown` · `standUp`, 효과음은 `sfx`. 키 높이 단위 `H` = `walk.scale` (도시 `SCALE_CITY` 0.55, 건물 안 `SCALE_IN` 1.35). 속도 · 높이는 "키의 몇 배"로 적혀 있다.

## 1. 느낌 말 → 변수

| 들리는 말 | 먼저 볼 변수 |
| ---- | ---- |
| 둥둥 뜬다 · 무겁다 | 꼭대기까지 시간(점프 속도 / 중력), 오를 때 · 떨어질 때 중력 비, 공중에서 속도 유지 |
| 둔하다 · 늦게 반응 | 누른 뒤 움직이기 시작하는 프레임 수, 가속(키/초²), 돌기 속도(도/초) |
| 미끄럽다 | 감속, 최대 속도까지 시간, 키를 뗀 뒤 멈추기까지 거리 |
| 점프가 씹힌다 | 착지 직전 누름이 버려지는가(버퍼 없음), 턱에서 떨어지는 중 점프 불가(코요테 없음), 받침 모서리 |
| 카메라가 출렁 · 튄다 | 카메라 따라가기 속도(3인칭 12/초 · 1인칭 30/초), 한 프레임 최대 각도 변화, 건물 가림으로 당겨지는 거리, `walk.lag` 이 메우는 순간 이동 |
| 치이는 게 밋밋하다 | 날아가는 속도 · 높이, 구르는 속도, 화면 흔들림 · 멈춤 유무, 소리 |
| 할 게 없다 · 목표를 모르겠다 | 손맛이 아니다. `/game-review` 로 |

표에 없으면 후보 변수 2~3개를 제안하고 어느 쪽인지 묻는다.

## 2. 계산

`updateWalk` 의 숫자로 결과를 낸다 (높이 = 속도² / (2 × 중력), 꼭대기 시간 = 속도 / 중력). 키 단위로 적고 도시 · 건물 안 두 크기를 함께.

- 점프 높이 · 꼭대기 시간 · 공중 시간, 오를 때 · 떨어질 때 중력이 같은지
- 걷기 · 달리기 · 뒷걸음 최고 속도까지 시간, 키를 떼고 멈추기까지 시간 · 거리
- 돌기 속도 (걷기 · 달리기), 3인칭 카메라가 등 뒤로 돌아오는 시간
- 차에 치임: 날아가는 속도 · 높이, 구르는 바퀴 수, 넘어진 채 있는 시간

참고값(다른 3인칭 게임에서 흔한 범위, 정답 아님): 점프 꼭대기 0.3~0.45초, 떨어질 때 중력을 오를 때의 1.5~2배, 코요테 0.08~0.12초, 점프 버퍼 0.1~0.15초, 걷기 최고 속도까지 0.15~0.3초. 범위 밖이면 "참고값과 다름"으로만 적고 고칠지는 사용자가 정한다.

## 3. 실측

실험실로 실제 도시를 화면 밖에서 열고 매 프레임 기록한다.

```bash
node scan.js <저장소> -o output/feel.html --no-open
npx electron .claude/lab/lab.js output/feel.html feel <스크래치>/feel.json
```

`feel.json` 의 `jump` · `walk` · `run` · `turn` · `runJump` · `knock` 은 프레임 배열이고 열 이름은 `columns` 에 있다 (`jy` 는 발이 뜬 높이, `v` 는 앞 속도, `H` 는 키). 스크래치에 작은 스크립트로 2단계 값과 비교한다.

| 잴 것 | 방법 | 비교 |
| ---- | ---- | ---- |
| 점프 높이 · 꼭대기 시간 | `jump` 의 `jy` 최대값과 그 시각 (키로 나눈다) | 2단계 값과 ±0.03 키 · ±1 프레임 |
| 가속 · 멈춤 | `walk` · `run` 의 `v` 가 최고의 90% 에 닿는 시간, 뗀 뒤 0 까지 시간 · 거리 | 2단계 값 |
| 돌기 | `turn` 의 `heading` 변화율 | 2단계 값 |
| 카메라 | 프레임마다 카메라 위치 변화, 가장 큰 한 프레임 이동 · 각도 | 튐이 있으면 그 프레임의 `jy` · 위치 변화와 함께 |
| 차에 치임 | `knock` 의 날아간 거리 · 최고 높이 · `tumble` 이 0 으로 돌아오는 시간 | 2단계 값 |

화면 밖 프레임은 실제 창보다 느리고 고르지 않다. 시간은 프레임 수가 아니라 `t` 로 잰다. 손으로 해 봐야 아는 것(눌렀을 때 반응이 느낌상 늦은지)은 "사람 확인 필요"로 적는다.

## 4. 피드백 표

일마다 지금 있는 피드백을 코드에서 찾아 채운다 (파일:줄).

```
| 일 | 크기 | 몸 (찌그러짐 · 자세) | 카메라 | 소리 | 글자 · 표시 | 비어 있는 것 |
```

일: 걸음 · 달리기 · 점프 · 착지(세게 · 살짝) · 받침 위 착지 · 벽에 막힘 · 차에 치임 · 서 있는 차에 막힘 · 앉기 · 일어서기 · 건물 문 · 엘리베이터 · 층 이동 · 코드 모니터 열기.

크기는 작게 · 중간 · 크게 세 단계. 작은 일(걸음 · 착지)은 몸 · 소리만, 중간(점프 · 앉기)은 몸 + 소리, 큰 일(차에 치임 · 건물 들어가기)은 카메라 · 화면까지. 작은 일에 큰 피드백, 큰 일에 피드백 없음, 결과가 0.5초 안에 안 보이는 것을 찾는다.

## 5. 규칙 점검

- 카메라가 한 프레임에 튀지 않는가 (발밑 높이가 한 번에 바뀌는 곳: 받침 · 구역 턱 · 앉기 · 일어서기 — `walk.lag` 이 메우는지).
- 카메라 흔들림을 넣는다면 그리기(카메라)만 움직이고 주인공 위치 · 충돌은 그대로인가.
- 멈칫(긴 프레임)이 동작에 붙어 있지 않은가 (`/playtest` 의 동작별 멈칫 표).
- 소리를 끈 사람도 알 수 있게 몸 · 화면 피드백이 있는가 (설정에서 효과음 끔).

## 6. 보고

결론 한 줄(가장 손맛을 해치는 것 하나) → 1단계 변수 → 2 · 3단계 계산 · 실측 표 → 4단계 피드백 표 → 5단계 점검 → 제안:

```
| 변수 | 지금 | 제안 | 노리는 느낌 | 확인 방법 (3단계 어느 측정) |
```

느낌의 수용 기준을 숫자로 함께 제안한다 (예: "점프 꼭대기 0.35~0.4초", "카메라 한 프레임 각도 변화 2° 이하"). 숫자를 바꾸는 건 승인 뒤 별도 작업이다.

## 하지 않는 것

- 게임 코드 수정 (이 스킬은 재고 제안까지)
- 참고값을 정답처럼 쓰기. Repopolis 의 기준은 사용자가 정한다
- 실측 없이 "반응이 느리다" 단정, 화면 밖 프레임의 fps 를 실제 성능처럼 쓰기
